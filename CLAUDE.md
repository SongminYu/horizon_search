# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A structured dataset of **EU Horizon research funding** (Horizon 2020 + Horizon Europe) in energy / environment / climate / food-agriculture / transport, plus a static query website (the "Pivot Explorer"). It is a **data product**, not a software application — no test suite, build system, or package manifest; the pipeline uses only `pandas`, `openpyxl`, `sqlite3`, and the Python standard library (network via `urllib`, no `requests`, no API keys).

Scope is **Horizon-only**: 9 project blocks — CL4, CL5, CL6, EU Missions (MISS), and H2020-SC2/SC3/SC4/SC5/JTI. (JU, LIFE, and Innovation Fund were removed; the OpenAlex paper-institution layer was removed — "organisation" means only a CORDIS funded participant.)

## Data flow (the important picture)

```
raw/ (CORDIS bulk + OpenAlex cache)          gitignored, re-downloadable
   │  collection scripts (per block)
   ▼
data/<block>_Topics_and_Projects.xlsx        gitignored, TRANSIENT build intermediate
   │  build_database.py
   ▼
eu3e.sqlite                                  ★ the committed master database
   │  export_webapp.py
   ▼
webapp/data/*.json                           the static site's data (committed)
   │
   ▼  webapp/index.html  (vanilla-JS Pivot Explorer)
```

**`eu3e.sqlite` is the committed master and single source of truth.** Two update paths:
- **Routine / incremental** — edit `eu3e.sqlite` directly (it's a normal SQLite file; every field the site uses lives there), then `export_webapp.py`. `data/` is not involved.
- **Full re-collection** (new CORDIS/OpenAlex bulk) — re-download `raw/` → collection scripts regenerate `data/` (transient) → `build_database.py` rebuilds `eu3e.sqlite` → `export_webapp.py`.

`data/` and `pipeline/raw/`,`pipeline/parsed/` are all gitignored build material; their content is fully captured in `eu3e.sqlite`.

## Layout

- `eu3e.sqlite` — **committed master database** (Horizon-only; tables below)
- `webapp/` — static SPA: `index.html` + `webapp/data/*.json` (generated by `export_webapp.py`, committed)
- `pipeline/scripts/` — Horizon-only collection scripts (build workbooks) + `build_database.py` + `export_webapp.py`
- `data/`, `pipeline/raw/`, `pipeline/parsed/` — **all gitignored, transient**; `data/` = workbook build intermediate, `raw/` = CORDIS/OpenAlex downloads + the `raw/people/` work cache + `raw/works_doi.json`, `parsed/` = regenerable intermediates. Everything here is captured in `eu3e.sqlite`.
- `webapp/apikey.local.js` — **gitignored, local only**; sets `window.GEMINI_API_KEY` for the LLM search. Not committed, not deployed.
- `README.md`, `WORKLOG.md` — Chinese; README is the entry point; WORKLOG is the original collection log (references the pre-Horizon scope in places).

## SQLite schema (`eu3e.sqlite`)

Five entities + relations (built by `build_database.py`):
- `topic`(id, title, destination, block, type, budget_eur_m, status) · `topic_keyword`(topic_id, keyword)
- `project`(grant_id, acronym, title, block, eu_contribution_eur, start_date, end_date, status, coordinator, coordinator_country, topic_id, objective)
- `unit`(org_id, name, country, activity_type, sme, total_ec_eur, n_projects, coordinator_count) — CORDIS funded partners
- `project_unit`(grant_id, org_id, ec_eur) — participation with each partner's EU money
- `researcher`(author_id, name, orcid, country, main_institution, works_total, lead_works, topics) — filtered to ≥1 lead OR ≥2 works
- `project_researcher`(grant_id, author_id)
- `work`(work_id, title, year, doi, url) · `work_project`(work_id, grant_id) · `work_author`(work_id, author_id)
- `meta`(key, value) — `blocks` JSON + `doi_pct`

## AI-callable search (CLI + MCP)

The webapp's two-stage Gemini search, ported to the command line so another AI agent can run it and read the result from a file (instead of loading the whole DB into context). Reads `eu3e.sqlite` directly; stdlib + `urllib` only (the MCP wrapper additionally needs `pip install mcp`). Gemini key resolves from `$GEMINI_API_KEY`, else `webapp/apikey.local.js`.

- `pipeline/scripts/eu3e_search.py` — the core. Same two-stage flow as `llmSearch()` (stage 1 coarse over all 7,242 projects → ≤100 ids; stage 2 scores them 0–100 + reason → top N). For each hit it JOINs out the full project record + topic + top participant units + linked researchers. It creates a **new folder `eu3e_search_<slug>/` under `--out-dir`** (default cwd) containing **`results.json`** (rich, canonical) + **`README.md`** — and the README is an *AI-facing doc* (`render_readme()`): what tool/steps produced it, the Horizon scope & money/people caveats, the JSON data dictionary, usage tips, then a scan-table. stdout prints a short summary + paths.
  ```bash
  python3 pipeline/scripts/eu3e_search.py "海上风电退役与回收" --out-dir . --top 30
  ```
- `pipeline/scripts/eu3e_mcp.py` — a `FastMCP` server exposing one tool **`search_eu3e(query, out_dir=".", top=50)`**; it calls `run_search()`, writes the files into `out_dir`, and returns only a short text summary (paths + top hits) so the heavy data stays on disk. Registered **user-scoped** so every Claude Code window (any directory) can call it: `claude mcp add -s user eu3e -- python3 <abs>/pipeline/scripts/eu3e_mcp.py`. When calling the tool, pass your session's working directory as `out_dir` so the output lands where you invoked it.

`run_search()` is the shared entry point (both the CLI `main()` and the MCP tool call it); a faithful CLI port keeps in sync with `SEARCH_CFG`/`PROMPTS` in `index.html`.

## Running the site

```bash
cd webapp && python3 -m http.server 8742   # http://localhost:8742 (fully static, no external deps)
```

The webapp loads the 5-layer graph (`graph_meta.json` + `nodes_{topics,projects,units,people,works}.json`, ~47MB once) where nodes reference neighbors by **integer index** into the other layers' arrays. Modes:
1. **Keyword 全景 dashboard** (`#/q/<query>`, `dashboard()` → `llmSearch()`) — **Gemini two-stage semantic search** over a natural-language description (see below). Result = a ranked, scored project set shown as 3 **tabbed tables** (项目 / 参与单位 / 人, 50/page); the 项目 table shows each project's relevance score + one-line reason. Two **networks** (参与单位 = CORDIS co-participation, sized by EU€; 人 = co-authorship) open as **modal overlays** from icons at the card's bottom-right — canvas force-graphs (`drawNet()`) with semantic zoom + cached layout.
2. **Entity pivot** (`#/{t,p,u,r,w}/<idx>`) — one `view*` per type, breadcrumb trail. Project / researcher pages are tabbed tables; unit / topic pages are a full-width project table; the work page is a single page (title + DOI + abstract fetched live from OpenAlex + clickable author/project chips).
3. **History** (`#/history`, `viewHistory()`) — every search is saved to `localStorage` (query + ts + ranked results, by grant_id; up to 100, deduped by query). The 历史 header icon opens a table to re-enter (restores instantly, no re-call) or delete past searches.

Five entity layers: **topic / project / unit (CORDIS partner) / researcher / work**. Within-context metrics (e.g. papers-in-this-project) are computed client-side, not global totals.

### Gemini search (the keyword 全景)

All client-side, no backend. Requires `webapp/apikey.local.js` (gitignored) setting `window.GEMINI_API_KEY`; without a key the dashboard shows a setup note (search is key-gated by design). The code is grouped near the top of the `<script>` block: `SEARCH_CFG` (model `gemini-2.5-flash`, `stage1Max:100`, `finalTop:50`, output-token caps), `PROMPTS.stage1`/`stage2`, `SCHEMA_IDS`/`SCHEMA_SCORES`, `geminiCall()`, the tolerant parsers, and `llmSearch()`.

- **Stage 1 (coarse)** — sends the whole `proj_catalog.json` (all 7,242 projects: `[grant_id] acronym — title :: 300-char objective snippet`, ~0.6M tokens) + the query to Gemini; returns up to 100 candidate grant_ids. Schema is a flat `ARRAY` of `INTEGER` with `maxItems:100`.
- **Stage 2 (fine)** — pulls the candidates' **full** objectives (from `objectives_<BLOCK>.json`) and asks Gemini to score each 0–100 (5-pt rubric) with a one-line reason; takes the top 50, sorted desc. Schema is an `ARRAY` of `{g,score,reason}` objects — **no `maxItems`** (a length cap on a nested-object array triggers Gemini's `400 too many states for serving`; the count is bounded by the prompt + `maxOutputTokens` + client-side slice instead).
- **Robustness:** `thinkingConfig.thinkingBudget:0` (output budget goes to the answer, not thinking); `finishReason` is checked (SAFETY/MAX_TOKENS); tolerant parsers (`parseIdArray` regex-salvages ids, `parseObjArray` keeps complete objects) survive truncation. Each search runs under an `AbortController` that `route()` aborts on navigation, so leaving the page cancels the in-flight call.
- **Cost/latency:** ~one Stage-1 call (~0.6M input tokens) + one small Stage-2 call ≈ 30–60s, ~$0.2/query on paid Flash. No context caching yet (a future optimization).

## Pipeline architecture (building the workbooks → DB → site)

Each Horizon block builds its workbook in three stages (per-block prefixes `cl4_`/`cl6_`/`miss_`; unprefixed = the original CL5 set; `h2020_build_workbooks.py` does all five H2020 blocks):
1. `*_build_topics_from_cordis.py` — filter CORDIS bulk → topic skeleton
2. `*_fetch_details.py` (or `fetch_topic_details.py` for CL5) — F&T Portal `topicDetails` (file-cached, polite rate-limit)
3. `*_merge_to_excel.py` — write Topics + Projects sheets

Then the other three sheets (only touch their target sheet, preserve manual edits):
```bash
python3 pipeline/scripts/add_participants_sheet.py <projects_pkl_stem> <workbook.xlsx> [raw_subdir]
python3 pipeline/scripts/add_organisations_sheet.py <projects_pkl_stem> <workbook.xlsx>
python3 pipeline/scripts/fetch_people.py <workbook.xlsx>      # OpenAlex by Grant ID → raw/people/ cache + People sheet pkl
python3 pipeline/scripts/add_people_sheet.py <workbook.xlsx>
python3 pipeline/scripts/enrich_works_doi.py                  # DOI links for cached works → raw/works_doi.json
```
The **People** sheet is researcher-level from OpenAlex (`awards.funder_award_id` = Grant ID), ranked by Lead Works (first/last/corresponding). Then:
```bash
python3 pipeline/scripts/build_database.py    # data/*.xlsx + raw/people cache + works_doi → eu3e.sqlite
python3 pipeline/scripts/export_webapp.py     # eu3e.sqlite → webapp/data/*.json
```

`build_database.py` holds the `PROGS` registry (9 Horizon blocks → block keys) and the researcher merge/filter. `export_webapp.py` reads only the SQLite. Both are stdlib + pandas.

External deps: `pandas`, `openpyxl`, system `pdftotext` (poppler) for the collection stage. `raw/` re-downloaded before a from-scratch rerun (see WORKLOG).

## Conventions to preserve

- Scripts resolve paths via `ROOT = Path(__file__).resolve().parent.parent` (= `pipeline/`); workbooks at `ROOT.parent/"data"`, SQLite at `ROOT.parent/"eu3e.sqlite"`. Run from repo root.
- All displayed text is run through a `clean()` (strip HTML tags like `<sup>`, decode entities) at build time so titles/names never render as markup/mojibake.
- **Two money calibres, never additive**: `eu_contribution_eur` / signed EC (CORDIS actual) vs the topic's `budget_eur_m` (work-programme indicative). H2020 topics lack budget/keywords/TRL (only HE topics have them) — those fields are null for H2020.
- The **People/works layer is an OpenAlex co-authorship proxy**, not official project roles. Coverage is a gradient: ~44–70% of projects have linked papers (high for RIA/IA research, ~0 for CSA/support and brand-new projects). Empty papers/researchers on a finished project is usually correct (CSA), not a data gap.
- "Organisation" = **CORDIS funded participant only** (`unit`). OpenAlex paper-signed institutions are intentionally not modelled.
